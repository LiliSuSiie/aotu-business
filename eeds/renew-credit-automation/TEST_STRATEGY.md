# 测试策略与实现依据

## 已核实的实现

| 能力 | 代码实现 | 自动化检查重点 |
| --- | --- | --- |
| 数据跑批 | `RenewCreditCustomerService.exeBatchData` | 任务状态、筛选、幂等、模型结果 |
| 文件跑批 | `exeBatchFile` | 开关、批次隔离、文件内容、上传失败 |
| 数据更新 | `exeUpdateData` | 游标分页、到期日、客户确认及结果同步 |
| 列表/确认 | `/renew/credit/customer/list`、`/confirm` | 数据权限、状态过滤、重复确认 |
| 手动批任务 | `TaskManualExecuteController` 的 `renew/doData`、`renew/doFile`、`renew/doUpdate` | 日期参数、并发互斥、任务日志 |

注意：当前代码的 `renew_credit_customer` 只有单个 `CODE` 字段；需求优化中提出的 `renew_credit_customer_batch` 与“每次模型调用新 Code”尚未在此基线中出现。因此优化用例是**待实现功能的验收集**，不能用当前版本判为通过。

## 分层策略

1. **数据库验收（主层）**：验证候选客户、`batch_task_log`、`renew_credit_customer`、模型记录及优化后的批次表的最终状态。这是批任务正确性的唯一可靠证据。
2. **接口回归**：验证列表、确认、进件列表和受保护的手动入口；使用真实 Token，不在测试资产保存凭证。
3. **任务/外部依赖联调**：用模型服务桩记录模型顺序和入参，用 SFTP 测试目录验证文件，避免对真实征信和朴道发起查询。

## 必备测试数据

每条客户数据必须有独立身份证号、合同号和批次日期，并在执行后清理。至少准备：

- 合同到期日：当天、+90 天、+91 天、已过期；合同状态：`EFFECTIVE` 与非有效。
- 年龄：24、25、64、65 周岁；有效、无效、缺失白名单。
- `oldlcno` 可/不可截取进件 ID；进件缺失；首贷（非 `loanType=2`）和历史续授信。
- 两位客户经理（本人和无权限用户），以及同证件号不同原合同的客户。
- 模型桩返回：通过、拒绝、异常、审批中；外部征信调用计数器。

## 通过门槛

- P0/P1 用例 100% 通过；P2 仅可因已登记的外部依赖不可用而阻塞。
- 所有任务无 `executing` 残留；异常时任务日志为 `exception` 且客户不对外展示。
- 同一测试批次的模型记录、结果表和客户记录必须可追溯；优化版必须以批次调用 Code 追溯。
- 每个会写库的场景必须提供清理 SQL 或在可整库回滚的测试企业运行。
