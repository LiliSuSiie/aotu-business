# 泰安评议业务：1000 户批量自动化方案（实跑修订版）

## 最新行为：连续选择、复评议与补充评议支持（2026-09-18）

当前程序支持类型 1（首轮评议）、类型 2（常规性复评议）和类型 4（补充评议）的要素模式，均沿用用户确认的全 true 测试规则。类型 3 是整改性复评议，本次未启用。完成一名评议员后刷新名单，有未完成人员时询问 y／n；选择 y 后重新查询并选择下一人，全部参与人员完成后自动结束。`--dry-run` 和大于 0 的 `--limit` 一次只处理所选一人。常用命令为 `python taian/scripts/run_review.py --no-report`（项目根目录执行）。

补充评议保留系统已办列表中的历史有效结果，只对当前待办户进行整户保存和当前批次明细回查。待办清零、已办非空但人员状态未完成时，可只保存完成状态。该类型的 recordsTotal 可能为本页条数，分页改为以独立户数统计为目标，同时校验前后统计、数量和唯一性，防止漏户。

类型含义和详情接口分支已与本机后端源码核对；复评议预览中的历史值不能替代当前批次已办明细验收。每人进度隔离，接口结构、户数、台账和回查均有校验；未知写入不自动重试。当前新增行为通过本机模拟接口测试，尚未对当前真实批次进行写入验收。最新操作说明见 [新手运行指南](README.md) 与 [技术运行说明](scripts/README.md)。

## 3. 真实接口链与数据关联

以下业务路径省略公共前缀 `/xczx/backend`。列表接口虽然使用 POST，仍须按具体语义区分查询和写入。

| 阶段 | 方法与路径 | 输入、输出及处理 |
| --- | --- | --- |
| 获取有效会话 | `POST /comm/v1/user/login` | #1；新版每次从配置加密用户名密码并登录，使用响应 Token 和企业标识；失败即停止，不回退到旧会话，自动中途续期未启用 |
| 查询评议批次 | `GET /mobile/village/appraise/info/list` | #2；支持录制中的 `page`、`rows`；按明确目标匹配批次 `code`，不能默认第一条 |
| 查询候选评议员 | `GET /mobile/village/trustee/pulldown/list` | #3；`appraiseInfoCode`、`villageCode` |
| 保存参与名单／收尾状态 | `POST /mobile/village/appraise/info/resident/save` | #4、#28；初始化选择与收尾分开处理，本次读取最新名单，仅将目标人员设为 3，其他人员字段原样保留 |
| 查询本批次评议员 | `POST /mobile/village/appraise/info/trustee/list` | #5、#29；返回名单的 `code` 用于后续 `appraiseTrusteeCode` |
| 查询评议员进度 | `POST /mobile/village/appraise/info/resident` | #6、#30、#33；读取总户数、One/Two 户数 |
| 分页查询户 | `POST /mobile/village/appraise/info/resident/list` | `appraiseInfoCode`、`appraiseTrusteeCode`、`page`、`rows`；**appraiseState=2 待办、1 已办**；读取 recordsTotal |
| 查询整户成员和结果 | `GET /mobile/village/trustee/detail/info` | `appraiseInfoCode`、`trusteeCode`、加密后的 householderIdNumber；**appraiseState=1 未评议详情、2 已评议结果**，与列表相反 |
| 查询批次配置 | `GET /mobile/village/appraise/info/type` | #9 等；参数 `code`；检查批次有效性、评议类型与配置 |
| 查询不宜授信类型字典 | `GET /comm/sys/dict/items` | #10 等；`code=bysxlx`；作为输入合法性校验依据 |
| 保存整户评议 | `POST /mobile/village/trustee/detail/save` | #11、#16、#21、#26；两个批次／评议员关联字段，加 `list[i]` 成员和 `list[i].list[j]` 要素 |

关键关联规则：

- 批次列表 `code` → `appraiseInfoCode`；数据库 `id` 与业务 `code` 不混用。
- 评议员列表 `code` → 查询列表和保存时的 `appraiseTrusteeCode`；户详情接口使用参数名 `trusteeCode`。
- 户列表 `householderIdNumber` 明文 → 按页面 AES-ECB／PKCS7 规则加密为十六进制密文 → 整户详情查询。直接传明文可能返回业务成功但空列表，这是原方案遗漏且本次已修复的步骤。新版脚本使用用户明确提供的协议密钥，以 hh01 的已知密文做启动自检，用户名、密码及详情查询共用同一加密函数，不依赖前端源文件。
- 户详情 `appraiseResidentCode` → 保存 `list[i].appraiseResidentCode`。
- 成员详情 `list[j].appraiseInfoElementCode` → 保存同一成员对应的要素编码。
- 详情中的要素值字段为 `useElement`，保存字段为 `isUseElement`；读取、提交和回查必须显式映射。
- 当前名单查询及完成保存的后端实现按 appraiseInfoCode 解析关联，不要求另填 villageCode；若所选列表明确返回 villageCode 则传入，不用 villageId 冒充，也不复制旧批次村码。其他部署仍应验证此契约。
- 列表和详情的 appraiseState 含义相反，必须独立映射。批次 appraiseStatus 本次为数字 0，而响应业务 code 为字符串 "0"；预检曾因类型假设被阻断，已修正并重验后才开始写入。

## 4. 1000 户如何运行

### 4.1 固定任务清单

1. 输入环境、企业、目标评议批次、参与评议员和本次目标户范围。产品身份由明确配置确认，不能从文件名推导产品码。
2. 检查有效会话、批次有效性及参与名单；若名单已正确，直接复用。需要名单初始化时，仅在初始化阶段执行一次，并回查成员和状态。
3. 暂不提交评议，先按评议员完整分页查询待办，保存本次任务快照。录制只证明 `rows=10`；先沿用，增大分页大小前验证服务端限制。
4. 按“环境／企业＋评议批次＋评议员＋家庭标识”去重，校验分页总数与唯一户数。检测翻页期间总数变化、重复页或缺页；出现变化时重新获取并对账，无法取得一致清单则暂停该批。
5. 明确 1000 户是用户提供的业务范围，还是该批次全部户。若接口有更多户，不能无条件取前 1000 条；若不足，也不能复制样本凑数。没有明确范围时仅产出候选清单。
6. 生成任务预览：涉及户数、评议员数、成员覆盖、规则版本、预期提交次数和异常项。准备完成后执行固定队列。

同一户需要 R 名评议员时，任务数是各评议员目标户数之和；仅当每人都评同样的 1000 户时才是 `1000 × R`。家庭成员随一户请求提交，不再把每名成员算作一户。

### 4.2 逐户执行

```text
取一个唯一的“评议员＋家庭”任务
  → 查询当前整户详情与已有结果
  → 验证家庭、成员、批次、评议员及要素集合
  → 匹配该评议员已确认的成员级评议输入
  → 如已有一致结果：登记已存在并核验，不重复保存
  → 如已有冲突结果：登记冲突，等待处理
  → 如待处理且输入完整：组装一次整户表单并保存
  → 检查 HTTP 与业务 code
  → 回查该户所有成员和要素值，确认待办状态变化
  → 持久化进度与证据，再处理下一户
```

快照生成后也需在保存前检查对象仍可评议。若人工或另一作业改变了状态，重新对账；不以旧快照覆盖新结果。

### 4.3 评议内容的数据来源

真实业务使用该评议员已确认的结果或已确认的确定性业务规则。每个成员的“是否了解、是否适宜授信、不宜授信类型及说明、评议要素、备注”都需要可追溯输入。缺失输入列为待补充，程序不自动填成 `true`，也不由 AI 猜测客户资产或评议信息。

如果本次用途是测试造数，可在隔离测试范围内选择“全部为 true”的样例规则，并另外准备 false、缺项和混合成员用例。固定规则可以一次定义后作用于全部指定测试户，无须逐户点击。

建议复用 JSON 作为输入资产，每项记录包含 `appraiseInfoCode`、`appraiseTrusteeCode`、家庭匹配标识、成员编码、成员评议值、要素编码和值、`ruleVersion`、输入来源和确认记录。允许不同评议员对同户有不同结果。

录制中同时存在空字符串和字面量字符串 `"null"`。应先验证服务端对缺省、空串、null 的处理，不能一律转换。不同批次的要素、字典和评议类型也不能沿用录制常量。

### 4.4 收尾与范围

每名评议员所有目标户核验通过后，回查统计和名单。前端代码及本次实跑已确认：待办列表清空后调用 resident/save，将目标人员 selectStatus 设为 3，页面才进入已完成分组。这是必需收尾。

执行前重新读取整份名单，仅改变目标评议员状态，保留其他人的最新字段；同一批次名单写入串行处理。回查状态、户数、全部成员和要素值，确认收尾没有改变明细。本次已经通过这些检查。如果本次只处理该评议员全部待办的一部分，不得提前设置整体完成状态。

录制没有证明整个评议批次已最终提交、审核通过、模型执行或授信额度生成。这些不纳入本次已证实范围；如业务验收需要，应补录后接入。

## 5. 确定性执行与中断恢复

优先由 k6 执行接口场景，外层本地调度器负责固定队列、持久化台账、分批启动和续跑。不依靠 k6 进程内变量承担跨进程恢复，也不直接把 1000 户配置成 1000 个并发用户。

- 台账建议使用本地 SQLite；每个任务使用唯一键防止重复领取，记录 `pending / running / verified / failed / unknown / conflict / blocked` 等状态。状态名称属于执行器设计，不是服务端枚举。
- **同一评议批次内写入先串行。** 本地对应整户保存入口有按 appraiseInfoCode 的 RedisLock，名单保存也按批次加锁。因此撤回同批次直接尝试 2—5 并发的建议；不同批次并发须另行验证部署版本、锁行为和统计一致性。
- 只对已确认的查询接口做有限次数退避重试。明细保存或名单保存发生超时、断网、5xx 时，登记 `unknown`，先回查是否已落库，不直接重放写请求。
- 发现已保存且值一致，恢复为成功；确定未保存且业务允许重试，才重新提交。部分写入、状态不一致或无法确认时隔离任务，不自动覆盖或删除。
- 台账记录提交前意图、请求摘要、响应关联号和核验结果。进程中断后，旧 `running` 任务先作为结果未知对账，不能直接重置待提交。
- 令牌过期停止领取新任务；恢复有效会话后核对企业与身份，从台账续跑。录制没有证明自动登录／续期可直接实现。
- 全局认证错误、权限异常或响应结构变化暂停批次；单户数据问题隔离后可继续其他户。每户有最大处理次数，避免坏数据导致死循环。
- 页面重复查询的批次配置、字典可以在同一批次内缓存；每批次、续跑和收尾前重新验证。成员详情和实际评议结果不能用全局缓存替代。

本地保存服务有事务，且已有居民记录会被更新、要素会删除重建，非空备注还可能追加，因此重复写入并非无副作用。默认对已有且一致的结果跳过写入，网络不确定时先对账。本地源码无法独立证明远端部署版本、数据库唯一约束及所有并发情形，本次未做故障注入或并发测试。

本次固定试验采用 Python＋JSON 台账＋本机进程锁，已验证先完成 1 户退出、下次继续 3 户，以及最终复跑 0 写入。规模化时建议升级 SQLite；新版已移除每户重复全量翻页，采用固定队列、逐户已办详情回查和最终全量集合／统计对账。

## 6. 验收与可复验证据

### 单户通过条件

1. 请求属于目标企业、批次、评议员和家庭，成员集合与当前详情一致，无串户、漏成员、重复成员或错绑要素。
2. 保存响应 HTTP 成功且业务 `code='0'`；仅有 HTTP 200 不算通过。
3. 通过可读取已评议结果的接口，逐成员比较评议值、要素值和不宜授信原因；保存接口返回空 data，不能据此证明内容落库正确。
4. 该户由待办转为已办，存在独立持久化明细 ID；详情 appraiseState=2 回查全部内容。本次已验证 11 名成员和 33 个要素，收尾及复跑前后明细 ID 摘要不变，复跑不新增写入。该证据是接口层结果核验，不等价于数据库全量唯一性检查。

### 批量通过条件

- 固定目标家庭集合去重后恰为用户指定的 1000 户；若多名评议员，分别对账每个人的任务集合。
- 所有目标任务都有最终分类，台账任务总数 = 已核验成功（含已存在且一致）＋失败＋结果未知＋冲突＋阻塞＋未执行，各分类互斥。全量成功要求非成功项均为 0。
- 核验通过的目标集合与计划集合一致。不能只用“最终待办 0”替代集合核对。
- 对只处理部分待办或已有历史完成的批次，使用初始基线和任务差集对账；不要求无关户待办清零，也不把历史结果算成本次新增。
- 需要的评议员收尾状态正确；第二次运行不会重复创建或无声覆盖结果。
- 若有外部人工操作，应单独标记差异，避免把其完成量归入自动化成绩。

### 首批必测场景

| 优先级 | 场景 | 可解释断言 |
| --- | --- | --- |
| P0 | 样例 4 户，成员数 4/3/2/2 | 四次整户保存覆盖 11 名成员，关联正确，结果回查一致 |
| P0 | 超过一页的 25 户，沿用 rows=10 | 全量快照为 25 个唯一家庭，执行后无漏户或重复 |
| P0 | 两名评议员处理同户 | 身份和结果独立，首人完成不会误跳过第二人 |
| P0 | 进程在提交后、记账前中断 | 续跑先回查，不重复提交已保存结果 |
| P0 | HTTP 200 但业务码失败 | 该户失败且不计入成功，不推进收尾 |
| P0 | 批次／成员／要素不匹配或输入缺失 | 写入前阻塞并指出具体字段 |
| P1 | 是否了解为 false、不适宜授信、原因缺失、混合成员 | 按经确认的条件必填和分支规则判断，不臆造预期 |
| P1 | 已完成／重复提交／部分保存／并发修改 | 一致结果跳过；冲突和部分结果隔离 |
| P1 | 会话过期、权限错误、限流、保存超时 | 可归因、有限重试、恢复后不串身份、不漏任务 |
| P1 | 要素增减、未知评议类型、批次关闭、名单变化 | 重新校验或阻塞，不使用旧模板强行提交 |

负向和重复写入用例在专用测试数据范围验证；当前录制只覆盖主成功分支，不能宣称这些分支已通过。

证据至少包含：运行 ID、环境／版本（版本取不到则标记未知）、录制摘要哈希、规则版本、任务脱敏键、步骤、耗时、HTTP 与业务码、服务端 requestId、请求／响应脱敏摘要、输入摘要、回查差异、失败归因和续跑记录。必要的原始证据存放在受控本地目录；通用报告不复制原始 Token、姓名、证件号和短信字段。

失败按系统缺陷、环境／权限、数据、脚本／断言、结果未知分类。修正脚本后重跑对应失败场景并保留前后证据；不要通过放宽断言掩盖系统缺陷。测试环境需有专用批次和清理口径；真实业务跑批不自动撤销已提交结果。

## 7. 工作量与执行时间口径

优化后每个“评议员＋家庭”通常包含一次详情读取、一次保存和一次或多次回查。名单／字典／类型为批次级开销，另加分页与统计查询。同一详情接口使用 appraiseState=2 回查已在前次实跑验证。

单名评议员 1000 户约为 3000 次以上核心请求，而不是重放 1000 次完整登录和页面初始化。三名评议员都覆盖 1000 户时约为 9000 次以上核心请求；额外重试、轮询和收尾另计。

同批次串行时，用 `目标任务数 × 单任务实测耗时＋准备／收尾时间` 估算。先通过 25 户／100 户试运行测量；本次 4 户请求包括预检、排错和重复强核验，不直接外推。原先依据未验证并发给出的 17／50 分钟演算不再作为本产品时长参考。
